# 服务架构模式总结

更新时间：2026-06-19

## 一句话结论

Linksee 当前采用“模块化单体 API + 静态前端 + 独立后台 Worker + 基础设施服务”的架构模式。

这不是微服务架构，也不是完整前后端分离 SPA 构建模式。当前更准确的描述是：

- 后端是一个 Express/Socket.IO 主进程，内部按领域模块拆分。
- 前端是静态资源，由后端 API 服务统一托管。
- Worker 是独立 Node 进程，用于定时和异步任务。
- MySQL、Redis、MinIO 是外部基础设施依赖。

## 服务组成

### API 主服务

位置：`apps/api`

职责：

- 提供 `/api/v1/**` HTTP API。
- 处理登录、JWT 鉴权和角色权限。
- 通过 Prisma 访问 MySQL。
- 通过 Socket.IO 提供在线状态、聊天和业务事件推送。
- 托管前端静态页面：
  - `/app` -> `apps/web/app`
  - `/demo` -> `apps/web/demo`

### Web 静态前端

位置：`apps/web`

职责：

- 提供正式页面和演示页面。
- 使用原生 HTML/CSS/JavaScript 实现当前工作台。
- 通过 API 服务访问业务接口。
- 通过 Socket.IO 客户端订阅实时事件。

当前没有独立 Vite/Webpack dev server，也没有正式 Vue/React 构建链。

### Worker 后台进程

位置：`apps/worker`

职责：

- 执行定时任务和异步任务。
- 当前已有提交截止扫描任务。
- 后续可承载文件处理、通知聚合、数据预处理等任务。

### 基础设施

- MySQL：核心业务数据。
- Redis：刷新令牌、在线状态、运行时状态、限流等。
- MinIO：提交文件、聊天文件等对象存储。

## 通信模式

1. 浏览器请求 API 服务。
2. 静态页面由 API 服务托管返回。
3. 业务读写通过 HTTP `/api/v1/**` 完成。
4. API 写库成功后发布业务事件。
5. Socket.IO 把业务事件推送给在线用户。
6. Worker 周期性执行后台任务，必要时复用 API 领域逻辑并写库。

## 关键设计原则

- 写操作走 HTTP，不走 Socket。
- 实时通道只推送状态和结果，不作为核心命令入口。
- 先持久化，再推送实时事件。
- 权限以后端判断为准。
- 前端隐藏按钮只改善体验，不能替代后端权限。
- Worker 不接用户请求，只处理后台任务。

## 当前优点

- 部署简单，服务数量少。
- API、Socket、静态页面同源，联调成本低。
- 领域模块已经按课程、项目、小组、提交、批阅、成绩、协作拆分。
- Worker 已具备独立进程形态，后续可以扩展后台任务。

## 当前风险

- 前端仍是原生静态页面，大型工作台维护成本会上升。
- API 主服务职责较多，需要继续保持模块边界。
- Worker 复用 API 代码时，要避免把 Express 上下文带入后台任务。
- 静态资源由 API 托管，未来若迁移 Vue/Vite，需要同步调整构建与部署链路。

## 运行观察指标

监控配置尚未落地为独立目录，短期先以以下指标作为运行观察清单：

- API 健康检查状态。
- 登录失败次数与限流触发次数。
- 阶段提交、批阅、成绩发布接口错误率。
- Review / Grade 敏感操作审计日志。
- Socket 连接数、心跳断开次数和重连情况。
- Worker 提交截止扫描的执行次数、失败次数和处理数量。

## 后续演进建议

短期：

- 保持 API 模块化单体，不急于拆微服务。
- 完善验收脚本和集成测试。
- 继续把后台扫描类任务迁入 worker。
- 对复杂工作台先用 Vue demo 验证交互设计。

中期：

- 为 `apps/web` 引入 Vue/Vite 构建链，逐步迁移教师端、助教端、学生端。
- 将前端构建产物输出到可由 API 或独立静态服务托管的位置。
- 把事件发布、权限判断、文件访问封装成更稳定的内部接口。

长期：

- 当 API 主服务出现独立扩缩容需求时，再考虑拆分服务。
- 文件处理、通知、AI/RAG 等重后台任务可优先从 worker 扩展，而不是拆核心业务 API。
