# 当前后端架构评估

更新时间：2026-06-19

本文档用于记录当前后端实现的现实状态，帮助团队在验收前统一认识：

1. 当前架构哪些地方是合理的
2. 当前架构哪些地方存在技术债
3. 为什么当前阶段不建议大规模重构
4. 后续如果继续演进，优先应收口哪些问题

## 一、总体判断

当前后端架构属于“领域拆分基本合理、业务链路已经成型、但路由层偏厚的实用型架构”。

它的优点是：

1. 课程、项目、阶段、小组、提交、批阅、评分、协作、组内任务等核心业务已经形成明确模块。
2. 权限控制与访问判断有一定复用，能够支撑真实教学协作场景。
3. 状态流转已经不再是单纯 CRUD，而是具备通知、会话、实时事件等副作用联动。
4. 当前已经具备较完整的后端集成测试基础，可以支撑验收前的回归验证。

它的主要问题是：

1. Router 过厚。
2. 副作用分散。
3. 协作域与教学域耦合较高。
4. 某些状态规则散落在多个模块中。

整体结论：

- 对当前交付和验收阶段来说，架构是可接受且可继续维护的。
- 不适合现在进行大规模重构。
- 更适合做“小收口”，即补测试、补文档、删冗余、统一口径。

## 二、当前做得比较合理的地方

### 1. 按领域拆分目录

当前 `apps/api/src` 已经按领域拆分为：

- `courses`
- `assignments`
- `groups`
- `submissions`
- `grading`
- `collaboration`
- `minitasks`
- `users`
- `auth`

这保证了后端结构至少不是“所有逻辑堆在一个目录里”的状态。

### 2. 权限校验有明确入口

当前大量路由复用了如下访问控制辅助逻辑：

- `ensureCourseReadable`
- `ensureAssignmentManageable`
- `ensureGroupManageable`
- `getGroupAccess`
- `ensureCourseMemberActive`

这说明权限并不是完全散写在每个路由中，后续维护成本相对可控。

### 3. 生命周期联动已经成型

当前系统已经支持以下典型联动：

- 课程激活/归档与课程会话、系统通知、小组归档联动
- 项目激活/归档与系统通知、小组归档联动
- 阶段开放/归档与系统通知联动
- 小组成组、组长变更与系统通知联动
- 提交、批阅、评分与实时事件联动

这说明后端已具备“真实业务系统”的行为特征，而不是单纯的数据接口集合。

## 三、当前最危险的地方

### 1. Router 过厚

这是当前最明显的技术债。

多个 router 文件同时承担了：

1. 参数校验
2. 权限判断
3. 事务操作
4. 状态流转判断
5. 系统通知
6. 聊天系统消息
7. Socket 事件推送

典型风险：

- 文件越来越长
- 修改一个接口时容易影响多个副作用
- 单元测试和集成测试的 mock 成本越来越高
- 业务规则不容易被复用

### 2. 副作用分散

当前通知、聊天系统消息、实时事件推送并没有完全收束到统一服务层。

副作用逻辑分散在：

- `courses-router`
- `assignments-router`
- `assignment-stages-router`
- `submissions-router`
- `reviews-router`
- `grades-router`
- `group-members-router`
- `group-lifecycle`
- `assignment-notifications`
- `minitasks-router`

这会导致：

1. 相似动作的副作用口径不容易完全统一
2. 后续新增业务时容易遗漏某个副作用
3. 通知规则修改时排查成本偏高

### 3. 协作域耦合较高

教学主流程已经和协作系统深度绑定，例如：

- 课程激活会启用课程群
- 小组成组会创建或激活小组群
- 提交会写入组内系统消息
- 组内任务会写入组内系统消息
- 批阅评分会推送实时事件

从产品角度这很合理，但从技术角度意味着：

- 聊天与实时系统的变化会影响教学主链路
- 协作侧 bug 可能影响教学侧核心体验

### 4. 状态规则分散

当前课程、项目、阶段、小组、提交、批阅、成绩都有自己的状态语义，虽然大方向已经明确，但实现仍散落在多个 router 和 helper 中。

典型风险：

1. 前后端口径容易靠记忆而不是靠统一文档
2. 新增一个状态副作用时，容易只改一处
3. 测试不够时，状态回归问题难以及时发现

## 四、为什么现在不建议大改

当前阶段项目已经接近验收冲刺，不适合再做：

1. 大规模 service 分层重构
2. 事件总线重构
3. 全量抽 repository/service/facade
4. 协作域与教学域重新解耦

原因很简单：

- 风险高
- 影响面大
- 很难在短时间内重新补齐联调与测试
- 对当前验收收益不如“补测试 + 补文档 + 删冗余”

## 五、当前阶段最值得做的小收口

### 1. 补测试

这是当前最有价值的事情。

优先覆盖：

- 生命周期成功链路
- 提交/批阅/评分回查
- 小组与任务协作链路
- 协作聊天基础成功链路

### 2. 补文档

重点统一：

- 状态口径
- 通知口径
- 归档与删除语义
- 哪些路由是当前正式入口

### 3. 删冗余接口和错误文档

已经确定前端不使用、且未来也不准备做的接口，应及时清理，避免后续误用。

### 4. 少量抽公共 helper

不建议大重构，但可以继续抽：

- 状态校验 helper
- 通知构造 helper
- 通用响应/参数解析 helper
- 聊天系统消息构造 helper

## 六、后续演进建议

如果项目在验收后继续发展，优先级建议如下：

1. 把重型 router 中的业务规则逐步迁移到 service/lifecycle 层
2. 把通知、副作用、实时事件进一步统一收口
3. 为协作域建立更独立的 service 边界
4. 继续扩大集成测试覆盖，尤其是列表查询、分页、筛选和任务/聊天组合链路

## 七、当前结论

一句话总结：

当前后端架构不是“最优雅”的，但对当前项目阶段来说是“基本合理、能够交付、适合小收口、不适合大重构”的状态。
