# 通知与接口最终收口清单

更新时间：2026-06-19

## 一句话结论

批阅 UI 大致完成后，最后收口重点不是继续扩页面，而是把“事件发生后谁能看到什么变化”讲清楚、接完整。建议把剩余工作拆成三类：

- P0：影响录屏验收主链路，验收前必须补齐或明确不演示。
- P1：不阻断主链路，但影响完整产品体验。
- P2：后续增强，不放进本次验收主线。

## P0：验收前优先收口

| 模块 | 当前状态 | 需要补齐 | 验收口径 |
| --- | --- | --- | --- |
| 批阅反馈通知 | 后端已有 `review.created`、`review.updated` 事件；批阅 UI 已能提交反馈 | 前端需要对 `needs_changes` 做强提醒；后端可补一条小组系统消息，提示“需要修改” | 学生端能明显看到需要修改；小组/提交详情能看到反馈 |
| 成绩发布通知 | 后端已有 `grade.published` 事件；教师端可发布成绩 | 前端需要对成绩发布做强提醒；建议后端补小组系统消息 | 学生端能看到成绩已发布，成绩页只展示 published 成绩 |
| 助教解绑接口 | 后端已有 `DELETE /api/v1/courses/:id/assistants/:assistantUserId` | 教师端助教列表需要有“解绑”入口并刷新助教列表 | 解绑后助教不能再进入该课程待批阅 |
| 助教绑定/解绑通知 | 后端有绑定/解绑接口，但缺用户级通知闭环 | 短期至少刷新助教端课程列表；正式方案走用户级通知，不进课程群 | 助教看到授权变化；教务/监管侧可追溯；学生不被打扰 |
| 项目附件删除 | 后端已有 `DELETE /api/v1/assignments/:assignmentId/materials` | 教师端项目附件列表补删除按钮，传 `objectKey` | 删除后项目附件列表刷新，错误附件不再展示 |
| 阶段附件删除 | 后端已有 `DELETE /api/v1/stages/:stageId/materials` | 教师端阶段附件列表补删除按钮，传 `objectKey` | 删除后学生端不再看到该阶段材料 |
| 实时事件前端类型 | 后端事件目录比前端 `event-handlers.ts` 更全 | 至少补 `review.updated`、`grade.updated`、`course.member.updated`、`group.member.updated` | 成绩调整、批阅修改、成员变化不需要手动刷新才能看到 |

## P1：主链路之后完善

| 模块 | 当前状态 | 建议 |
| --- | --- | --- |
| 用户级通知能力 | 当前 Socket 主要围绕 `course:*`、`group:*` 房间 | 新增轻量 `user_notifications` 或 `user:{userId}` 推送，承载助教绑定/解绑、教师指派/移除、账号停用/恢复 |
| 课程教师指派/移除通知 | 后端有教师指派/移除接口 | 增加 `course.teacher.assigned`、`course.teacher.removed` 或等价用户级通知，不进入课程群 |
| 批阅记录编辑入口 | 后端已有 `PATCH /api/v1/reviews/:reviewId` | 批阅历史中增加“编辑本次批阅”；若改成 `needs_changes`，触发学生强提醒 |
| 助教成绩草稿入口 | 后端允许助教创建/修改成绩草稿，但只能老师发布 | 若产品口径需要“助教建议分”，助教端补草稿创建/编辑入口；否则验收明确“助教只批阅，老师发布” |
| 阶段截止提醒 | 已有 worker 应用和提交截止处理基础 | 增加截止前 24h 提醒和逾期未提交待办，避免录屏链路里靠口头解释 |
| 项目/阶段通知语义 | 当前有 `assignment.created`、`stage.created` | 建议区分“草稿创建”和“正式激活/开放”：草稿不通知学生，开放才通知课程成员 |

## P2：后续增强

| 模块 | 建议 |
| --- | --- |
| 通知中心 | 做未读、已读、聚合、筛选，不急于本次验收 |
| 外部通知 | 邮件、企业微信、短信等只做后续增强 |
| 聊天搜索/编辑/撤回 UI | 后端路由清单已有消息 search/PATCH/DELETE，前端可后续补完整协作体验 |
| 文件处理通知 | 文件上传成功只刷新列表；处理失败再通知上传者或老师 |
| 每日/每周摘要 | 汇总待批阅、逾期、未提交、待发布成绩 |
| 已发布成绩调整 | 后端已有 `PATCH /api/v1/grades/:gradeId` 与 `grade.updated` 事件；本轮前端不提供入口 | 后续如恢复该能力，再补调整入口、原因输入、调整日志展示和 `grade.updated` 前端处理 |

## 通知事件整合口径

不要把所有事件都弹 toast。建议按下面规则接：

| 事件 | 前端显示 | 是否进入聊天 |
| --- | --- | --- |
| `review.created` | 学生反馈区刷新；`needs_changes` 强提醒 | 建议写小组系统消息 |
| `review.updated` | 当前反馈/提交详情刷新；关键状态变化再提醒 | 只有改成 `needs_changes` 时建议写消息 |
| `grade.published` | 学生成绩页强提醒；教师端状态刷新 | 建议写小组系统消息 |
| `grade.updated` | 后端保留事件；本轮前端不覆盖 | 后续恢复已发布成绩调整时再接入 |
| `submission.created` | 教师/助教待批阅数量增加 | 已有小组提交动态较合理 |
| `submission.status.updated` | 提交详情和状态刷新；需要修改时强提醒 | 不建议每次状态变化都写聊天 |
| `course.member.updated` | 课程成员列表刷新 | 不进聊天 |
| `group.member.updated` | 小组成员列表刷新；组长变化可提示 | 组长变化可写小组系统消息 |
| `course.assistant.bound/unbound` | 助教课程列表刷新，助教和教务有通知 | 不进课程群 |
| `course.teacher.assigned/removed` | 教师课程列表刷新，教师和教务有通知 | 不进课程群 |

## 录屏前检查顺序

1. 老师绑定助教后，助教登录能看到该课程和待批阅。
2. 如果解绑入口已补，演示解绑后助教失去该课程；如果未补，不录解绑，把它列为待补。
3. 老师上传项目附件、阶段附件后，学生端能查看/下载。
4. 如果附件删除已补，演示删除后学生端不再展示；如果未补，不录“清理删除”。
5. 学生提交阶段成果后，教师/助教端待批阅数量变化。
6. 老师或助教提交 `needs_changes`，学生端出现明确提醒。
7. 学生重交后，教师端待批阅恢复。
8. 老师发布成绩，学生端只能看到已发布成绩。
9. 已发布成绩调整本轮不录屏，不作为当前 UI 验收项。

## 不建议本次验收展示

- 登录/登出通知。
- 每个学生导入一条通知。
- 老师查看提交后给学生发“已读”通知。
- 文件上传进度通知。
- 心跳、在线状态、技术连接状态。
- 草稿项目、草稿阶段编辑通知。
